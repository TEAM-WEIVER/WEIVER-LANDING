# weiverai.com 모바일 스크롤 성능 분석 — 2026-10-14

반복 렌더링 비용이 확인된 지점은 상단 Canvas, 채용 일정 건수 텍스트, 매칭률 SVG다. 다만 **iOS 실기기의 프레임 드롭률과 지연 시간은 아직 측정하지 않았다.** 아래 숫자는 배포본을 Chromium 모바일 조건에서 비교한 처리 비용이며, iPhone의 체감 지연 시간으로 환산할 수 없다.

## 후속 관찰: 고정 장면의 떨림

2026-10-16 코드 및 WebKit 이슈 조사에서 공통 부모의 `overflow-x: clip`을 가장 유력한 후보로 좁혔다. [후속 조사와 로컬 비교 방법](../sticky/analysis.md)에 근거와 실제 기기에서 필요한 검증을 기록했다.

사용자가 제공한 iPhone 화면 녹화를 추가 분석했다. 고정 제목의 위치 흔들림은 원본 영상 기준 7~9px, 상단 로고는 정수 좌표 기준 0px였다. [영상 분석 보고서](../video/analysis.md)에 장면별 좌표, 연속 프레임 증거와 해석 한계를 기록했다. 프레임 드롭률이나 CPU 지연 시간을 실기기에서 측정한 결과는 아니다.

사용자는 iOS에서 장면이 고정된 동안 스크롤하면 화면이 떨리는 것처럼 보인다고 보고했다. 이 관찰에 따라 sticky 요소의 위치 안정성을 우선 확인해야 한다. 앞선 CPU·레이아웃 비교는 처리 비용의 기여도를 보여주며, 이 떨림의 원인을 확정한 측정은 아니다.

현재 구현은 스크롤 중 `scrollTo`로 위치를 되돌리는 방식이 아니라 `.hero`, `.sticky`, `.fit-sticky`, `.j-sticky`의 `position: sticky; top: 0`으로 요소를 고정한다. 고정 자체가 떨림을 필연적으로 만드는 것은 아니다. 확인할 코드 후보는 CSS의 `100svh` 높이와 JS의 `window.innerHeight` 진행률 계산을 혼용하는 부분, 고정 영역 내부 갱신으로 발생하는 레이아웃 변화다. 모바일 브라우저의 UI 변화와 viewport 단위의 관계는 [WebKit 설명](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/)에 있다. 실제 원인으로 귀속하려면 iPhone에서 주소창 상태·`innerHeight`·`visualViewport` 변화와 고정 요소의 `getBoundingClientRect().top`을 함께 기록해야 한다. 진입·해제 경계를 제외한 고정 구간에서의 top 좌표 범위(px)를 위치 흔들림 지표로 사용하고, DOM 좌표가 안정적인데 화면이 떨린다면 합성/표시 경로를 별도로 확인한다.

## 대상과 측정 조건

- 대상: https://weiverai.com, React 배포본. README의 `weiver-landing.vercel.app`는 다른 페이지여서 최종 분석에서 제외했다.
- 배포 JS: `index-C5Ap-GwH.js`. SHA-256 및 코드 대조 근거는 [deployment.json](deployment.json)에 보관했다. 저장소 HEAD는 `a6eec1799f487c6531d38156f6a30c6e5b059834`.
- 환경: macOS 26.5.1 / arm64, Ego Chromium 152. 화면 390×844 CSS px, 실제 기록된 DPR 2. DPR 3을 요청했지만 브라우저가 2를 보고하므로 실측값 2를 기준으로 해석했다.
- 터치 스크롤 입력: CDP `Input.synthesizeScrollGesture`, 아래로 1,600px, 요청 속도 500px/s. 구간별 시작점은 hero 0px, chapter1 2,600px, chapter2 4,900px, fit 11,000px, journey 15,400px.
- CPU throttling 4배를 요청한 비교 실험 및 1배의 상단/빈 페이지 대조군. 특정 iPhone 성능을 모사하거나 환산하는 조건은 아니다.
- 매 실험 페이지를 다시 열고 폰트 로드를 기다렸다. 각 조건 3회, 총 17조건·51회. 표는 3회 중앙값이며 원본 JSON에는 개별값이 있다.
- CDP `Performance.getMetrics`의 전후 차이, rAF 콜백 실행 시간, Long Task / Long Animation Frame을 수집했다. 페이지 로딩 시간은 측정 창에서 제외했다.
- 조건은 순차 실행했으며 무작위 교차 실험은 아니다. 실행별 스크롤 이벤트 수와 측정 창 길이가 달라 작은 차이는 개선으로 판정하지 않았다. GPU·래스터·실제 화면 표시 시간은 별도로 측정하지 않았다.

## 원인별 근거와 해석

### 1. 상단 Canvas가 계속 수행하는 계산과 그리기

코드: [TerrainCanvas.jsx](../../../apps/web/src/components/hero/TerrainCanvas.jsx#L48).

모바일 분기에서 50행×90점=4,500점을 그리고, 각 점에서 높이를 3번 계산하므로 그림 한 장에 높이 함수 13,500회가 실행된다. `dt > 30` 조건으로 일반적인 60Hz 환경에서는 약 30회/초 갱신을 목표로 한다. 매 갱신 시 삼각함수·지수함수, 50개 gradient와 총 1,500개 color stop, Canvas fill/stroke가 수행된다. 상단 밖에서는 그리기를 멈추지만 rAF 루프 자체는 유지한다.

Canvas 콜백만 건너뛰고 씬 재생을 유지한 실험에서 JS 누적 처리 **298.4→26.2ms, 91.2% 감소**, 전체 작업 **684.5→356.1ms, 48.0% 감소**를 관찰했다. 실제 스킵 여부는 JSON의 `skippedTerrain`에 기록했다. Canvas는 상단 JS 비용의 큰 기여원이다. 그러나 이 수치만으로 iOS 스크롤이 272ms 멈춘다고 주장할 수 없다. 영상 일시정지 버튼 실험은 Canvas와 씬 재생을 함께 멈추므로 둘의 영향을 합친 값이다.

### 2. 동일한 일정 건수 문자열을 스크롤마다 다시 쓰기

코드: [ContentSections.jsx](../../../apps/web/src/components/ContentSections.jsx#L125), 특히 135행의 `calc.textContent`.

건수는 정수이므로 대부분의 스크롤 이벤트에서는 값이 같다. 원본은 동일 문자열도 다시 쓰고, 같은 스크롤 갱신에서 CSS 변수를 변경한 뒤 다음 chapter의 `getBoundingClientRect()`를 읽는다. 서로 다른 스크롤 구독자의 읽기·쓰기까지 겹친다. 텍스트 노드 교체와 스타일 무효화가 반복 레이아웃을 만드는 구조다. 강제 동기 계산 위험은 코드 구조와 비교 실험으로 확인했고, 개별 호출의 강제 레이아웃 시간은 이 보고서에서 정확히 귀속하지 않았다.

동일 문자열일 때만 쓰기를 생략하면 레이아웃 **67→4회, 94.0% 감소**, 누적 레이아웃 시간 **29.8→4.3ms, 85.5% 감소**했다. 원본 횟수 범위는 65~121회, 중복 생략은 4~13회다. 이벤트 수 차이를 고려해 `전체 LayoutCount / chapter update 횟수`를 비교해도 중앙값 **1.015→0.074회/update**로 줄었다. 이 비율은 해당 구간 전체의 레이아웃을 update 횟수로 정규화한 값이며 해당 함수만의 비용은 아니다.

기능을 통째로 막은 실험의 67→2회는 기여도를 확인하는 대조 실험이다. 실제 수정은 마지막 표시 건수를 보관하고 값이 달라질 때만 `textContent`를 쓰는 방식이 적절하다.

### 3. 매칭률 SVG를 매번 다시 갱신

코드: [ContentSections.jsx](../../../apps/web/src/components/ContentSections.jsx#L352).

`ideal.points`는 고정값인데 매번 다시 쓴다. 진행률이 고정되는 구간에서도 `points`와 `stroke-dashoffset`을 다시 쓴다. SVG 도형 속성은 transform/opacity 갱신보다 레이아웃·그리기 부담을 만들 수 있고, 실제 실험에서도 반복 레이아웃을 관찰했다.

중복 SVG 속성 쓰기를 생략하면 레이아웃 **118→37회, 68.6% 감소**, 레이아웃 시간 **18.3→10.7ms, 42.0% 감소**했다. 원본 횟수 범위는 92~120회, 중복 생략은 36~71회. `전체 LayoutCount / fit update 횟수` 중앙값은 **1.044→0.410회/update**다. 애니메이션 중 실제 값 변경은 여전히 필요하다. 전체 작업 시간은 개선되지 않아, 고정 좌표를 초기화 때 한 번 설정하고 JS의 마지막 값과 비교하는 실제 구현으로 추가 검증해야 한다.

### 4. blur·brightness·drop-shadow는 이번 실험에서 미확정

후보 코드: [hero.css](../../../apps/web/src/styles/hero.css#L24), [content.css](../../../apps/web/src/styles/content.css#L200), [content.css](../../../apps/web/src/styles/content.css#L555).

세 요소의 filter를 브라우저 내 CSS로 제거했지만 상단·일정·서비스 단계에서 전체 작업 시간 감소가 일관되지 않았다. 상단 실험에서 단발성 151ms Long Task도 기록했다. iOS 렌더링 경로의 영향을 배제하는 결과는 아니지만, 현재 근거로 filter를 주원인으로 확정할 수 없다. 해당 실험은 세 filter를 함께 제거하므로 각 효과를 개별 분리하지도 못했다.

## 렉이 얼마나 발생했는가

**확정된 것은 위의 누적 처리 비용과 반복 레이아웃 기여도다. iOS의 실제 dropped frame 비율, 최악 프레임 지연, GPU 합성 지연은 미측정이다.**

원본 조건 6세트·18회에서 50ms 이상 Long Task는 0회였다. 그렇다고 스크롤 잔렉이 없다는 뜻은 아니다. 프레임을 구성하는 여러 짧은 작업과 렌더링이 함께 비용을 만들 수 있다. [Chrome의 Long Animation Frames 설명](https://developer.chrome.com/docs/web-platform/long-animation-frames)도 Long Task만으로 부드러움을 판단할 수 없는 한계를 설명한다.

프레임 계측의 대조군인 **빈 스크롤 페이지에서도** p95 rAF 간격이 약 50ms이고 최대 간격이 약 1,008ms였다. 따라서 원본에서 수집된 33~50ms 간격, 약 1초의 빈 구간과 `missedVsyncEstimate`를 사이트가 만든 프레임 드롭으로 귀속하지 않는다. 브라우저 운영·스케줄링의 영향을 분리하지 못했다. rAF 콜백 간격은 합성 스레드가 화면에 표시한 실제 스크롤 프레임 간격과도 다르다.

## 우선 수정 후보

1. 건수·점수·고정 SVG 속성은 실제 값이 달라질 때만 갱신한다. 고정 `ideal.points`는 초기화 때 한 번 설정한다.
2. 스크롤 처리를 한 rAF에 모으고, 모든 위치·크기 읽기를 먼저 수행한 뒤 스타일·텍스트 쓰기를 수행한다. 마지막 적용값 캐시와 화면 밖 구간 조기 반환을 함께 사용한다.
3. 모바일 Canvas 점 수·그리기 빈도를 줄이거나 스크롤 중에는 정지한다. 화면 밖·탭 비활성 상태에서는 rAF도 해제하는 방향으로 비교한다. 시각 변화가 있으므로 위 세 가지를 실제 구현한 후 다시 측정해야 한다.

애플리케이션 소스는 변경하지 않았다. 비교 실험의 변경은 측정 브라우저에만 적용했다.

## 측정 재현

실기기의 위치 떨림 비교는 [원인 조사 및 A/B/C 비교 안내](../sticky/analysis.md)를 따른다. 실제 분석에 사용하지 않은 별도 iOS rAF 측정기는 정리 과정에서 제거했다.

Chromium CPU 비교 실험은 [measure-mobile-scroll.mjs](../../../scripts/performance/cpu/measure-mobile-scroll.mjs)로 재현한다. 스크립트 상단의 `SPACE_ID`와 `ROOT`를 현재 환경에 맞추고 `config`의 region, variant, rate, repetitions를 지정한 뒤 `ego-browser nodejs < scripts/performance/cpu/measure-mobile-scroll.mjs`를 실행한다. 기본 config는 마지막 실험인 상단 Canvas 단독 정지 조건이다. 기존 TaskSpace는 종료됐으므로 현재 조사용 TaskSpace와 p1 페이지가 필요하다. 배포 JS 변경 시 callback 식별자와 대기 조건을 다시 확인해야 한다.
